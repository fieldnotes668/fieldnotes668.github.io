Email links / system design

A preview is not consent: one-time links in email

If simply opening a URL uses up a gift claim, an email security check or link preview can do the claiming before the recipient gets there.

An independent design example · October 2026
On this pageThe failure modeA safer request contractState and token dataTests worth runningSources

The failure mode

Imagine an email containing /claim/abc123. The server treats a GET request for that address as a completed claim and invalidates the token. The recipient later clicks the link and sees “already used.”

That request could have come from the recipient. It could also have come from software checking or previewing the link. Microsoft's Safe Links documentation describes URL checks during mail flow and again at click time, depending on the policy. HTTP itself treats GET as a safe method: the client is asking for a representation, not requesting a value-changing action. A claim endpoint that mutates state on GET conflicts with that expectation.

Keep two questions separate. “Can this URL be displayed?” and “Is this person authorized to claim this gift?” require different evidence. A request for the first should never silently answer the second.

A safer request contract

RequestServer behaviorState change
GET /access/{token}Show a neutral landing page. The response may explain the next step without revealing gift value or ownership.None
HEAD /access/{token}Return headers with the same safety expectations as GET.None
POST /access/{token}/confirmCheck the required authorization, token state, and request integrity. Apply the claim once.One atomic transition

The POST is a deliberate action, but a button alone is not a security boundary. Before changing state, verify the person or channel to the degree that the underlying gift requires. Protect the form against cross-site submission, and ensure the server checks the token again at commit time.

For a link that merely displays non-sensitive delivery status, the authorization threshold may be lower. For a link that reveals a redeemable code or transfers value, it should be stronger. The exact rule belongs in the product's threat model.

State and token data

Store a hash of the access token and a separate claim record. The URL token is a credential, so keep it out of analytics events, third-party embeds, and routine application logs. A page that contains token-derived data should use a restrictive referrer policy and avoid shared caching.

GET /access/{token}
  read token state
  render landing page
  do not claim, redeem, resend, or invalidate

POST /access/{token}/confirm
  verify requester and request integrity
  begin transaction
    lock claim record
    reject expired, used, or superseded token
    record one claim with an idempotency key
    mark token used
  commit
  return the result for that same claim

This is a sketch, not a drop-in implementation. A real system must define how the gift issuer confirms redemption, how an uncertain external result is reconciled, and whether the token permits viewing, claiming, or both. Never trigger a second external fulfillment call simply because a response was lost.

Tests worth running

  1. Fetch the link with GET and HEAD several times before a human opens it. The gift remains unclaimed.
  2. Submit the confirmation twice, including two concurrent requests. Exactly one claim is recorded.
  3. Replace a link, then revisit the old one. It cannot claim or reveal the gift.
  4. Open the landing page with an unknown token. The public response does not expose whether an order exists.
  5. Inspect logs and analytics. No usable gift code or access token appears.

The smallest useful rule is also the most important one: a read must remain a read. Put the value-changing action behind an explicit, authorized request and make its result repeatable.
