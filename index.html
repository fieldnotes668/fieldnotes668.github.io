What does “delivered” actually prove?

A useful status page tells people what the system knows, where that evidence came from, and what remains uncertain.

One purchase, several different facts

A checkout can succeed while an email is delayed. A delivery provider can accept a request without proving that the recipient saw it. A recipient can open a message without redeeming its gift. Compressing all of those facts into a single “sent” flag makes support harder and can tempt a system into an unsafe resend.

A better model separates the buyer’s intent, the order decision, the provider’s acknowledgement, and any later recipient action. Each layer has its own identifier and evidence source. This is a design pattern for a fictional service, not a claim about a specific issuer or delivery provider.

An evidence ladder

What happenedEvidence to keepWhat the UI can safely say
Order createdCommitted order and checkout idempotency key“Your order is recorded.”
Send queuedDurable job ID“Delivery is being prepared.”
Provider acceptedProvider request ID and acknowledgement“The delivery provider accepted the request.”
Recipient opened or redeemedA distinct, trusted event with a documented meaningOnly the specific action that event actually proves

A network timeout is missing evidence. It does not prove that the provider rejected the request. Before resending, reconcile using the stored request ID or move the job to a review state.

Design for the awkward minute after checkout

Suppose the provider accepts a send request, but its response is lost. The worker sees a timeout. A blind retry might produce a second message; telling the buyer to purchase again could create a second charge. The safer path is to keep the original order visible, mark the send outcome as uncertain, and ask the provider about the same request if its API allows that lookup.

For each state change, store an event ID, source, observed time, and the order or delivery job it belongs to. That small audit trail lets support distinguish a real provider rejection from a delayed acknowledgement. It also makes duplicate or out-of-order callbacks testable.

The public status view should omit gift codes, redemption URLs, full recipient addresses, and raw provider payloads. A status page is useful even when it has little data; it does not need to expose bearer-value material to explain a delay.
